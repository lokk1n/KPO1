# ВышКат

Консольное приложение для учета парка кикшеринга.

## Возможности

- Добавление самокатов, велосипедов, электровелосипедов, шлемов и зарядных станций.
- Проверка данных, уникальности ID и прохождение техосмотра перед добавлением.
- Вывод названий и инвентарных номеров всего имущества.
- Подсчет количества предметов и суммарного суточного энергопотребления.

## Запуск

Требуется Go 1.22.2 или новее

```
git clone https://github.com/lokk1n/KPO1.git
cd KPO1
go run .
```

## Архитектура и правила

| Модуль | Назначение |
| --- | --- |
| [contracts](contracts) | `Inventory` — ID и название, `Energy` — расход энергии, `Transport` — простота использования |
| [items](items) | Самокат, велосипед, электровелосипед, шлем и зарядная станция |
| [validation](validation/item.go) | Проверка ID, простоты и расхода энергии |
| [service_center](service_center) | Хранение парка, приём имущества, техосмотр и отчёты |
| [di](di/container.go) | Регистрация и создание зависимостей |
| [main.go](main.go) | Сборка приложения и консольное меню |

Модель использует структуры и интерфейсы. Каждый тип реализует только необходимые возможности. Например, велосипед не потребляет электричество, а зарядная станция не является транспортом.

[Park.Add](service_center/park.go) проверяет данные, уникальность ID и решение инспектора. [ServiceCenter](service_center/service_center.go) принимает потребителей с расходом **0,1–2,0 кВт·ч включительно**, а объекты без `Energy` — без дополнительных условий. Это выбранное учебное правило, техосмотр вызывается и для вещей.

[Reports](service_center/reports.go) считают всё имущество и энергию всех потребителей. Для новичков выбирается транспорт с `DifficultyLevel() >= 6`. Чем выше значение, тем проще управлять транспортом.


## SOLID

Принципы SOLID отражены в разделении моделей, валидации, техосмотра и консольного ввода. Интерфейсы `Inventory`, `Energy` и `Transport` описывают только нужные возможности. Разные типы имущества работают через общие контракты, сохраняя смысл ID и характеристик, а новые типы поддерживаются парком и отчетами без изменения их кода.

Наиболее явно выражена инверсия зависимостей (DIP): `Park` получает [Inspector](service_center/inspector.go) через конструктор, поэтому реальный техосмотр можно заменить тестовым без изменения парка.

Открытость для расширения (OCP) сознательно ограничена в [readItem](main.go): при добавлении типа нужно расширить меню и `switch`. Для пяти типов это проще отдельного реестра фабрик, доменная логика остаётся прежней.


## DI и тестирование

В [main.go](main.go) контейнер создает `ServiceCenter`, затем передает его в `NewPark`. Каждый `Resolve` вызывает фабрику заново, экземпляры не кешируются.

В [TestParkAdmission](service_center/park_test.go) через конструктор передается `StubInspector` с заданным решением. Тест проверяет принятие, отклонение и число вызовов инспектора. `TestMixedInventoryReports` фиксирует правило новичков на значениях 5, 6 и 10. [TestServiceCenterCheck](service_center/service_center_test.go) проверяет границы техосмотра. Также проверяются валидация, повторные ID, пустой парк и контейнер.



## Расширение


- **Транспорт:** добавить тип с `Inventory`, `Transport` и при необходимости `Energy`, затем дополнить меню. При существующих правилах парк и отчёты не меняются. Особый техосмотр потребует другой реализации `Inspector`.
- **Сотрудники:** отдельная модель и учет, поскольку сотрудники не ставятся на баланс. Текущие отчеты менять не нужно.
- **Склад:** поштучные запчасти можно представить через `Inventory`. Остатки, партии и списания потребуют отдельного модуля.


## Использование ИИ

ИИ помог проанализировать требования и код, написать проверки корректности ввода новых данных, подготовить тесты и провести тестирование. Предложенный код проверил и адаптировал под структуру проекта.
